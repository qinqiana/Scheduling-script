# 优化实施与验证（2026-09-06）

## 已完成

1. **硬冲突归因**：对既有四个黄金样例中的 49 条硬冲突逐条归类。当前输入未发现可直接证明的矛盾；这表示不能把它们称为无解，仍需继续改进求解器。
2. **独立规则校验**：增加不依赖引擎内部 `validateRoster` 的检查，覆盖请假、锁定、想休、加班、补休、晚班资格、晚接早、连续出勤、法定假与按组覆盖。人工构造的可行样例在三个种子下均为零硬冲突。
3. **后台生成**：生成改由一个工作线程执行。页面轮询进度，可取消；同时生成会返回 409；期间任意持久化修改会让计算结果作废而不写库。
4. **性能测量与优化**：用 CPU profile 定位到班次段修复和覆盖检查。将方案回滚及覆盖比较限缩在实际受影响的组，并复用覆盖需求；8 月固定种子从约 25.8 秒降至约 18.1 秒，黄金结果未变化。
5. **状态单一来源**：单格操作与 Excel 导入改走同一状态转换。补休现为锁定休息，以免“清空未锁定”留下补休标记却删掉休息格。
6. **单实例保护**：基于数据目录的命名管道租约，第二个进程不再打开同一数据库；进程退出后租约自动释放。
7. **界面反馈**：规则说明折叠；后台生成显示进度；硬冲突显示类别，带人员和日期的冲突可打开相应格子。

## 验证范围

- `npm run build`：前端、服务端和 Vite 配置类型检查，加生产构建。
- `npm test`：包含原有快照及新增诊断、不变量、后台任务、单实例、状态转换测试。
- `git diff --check`：补丁空白检查。

在 2026-09-07 使用 Node 运行环境兼容 shim 后，`npm test` 共 30 项通过、0 项失败，耗时约 53 秒；`npm run build` 已通过。

## 仍需关注

- 四个黄金样例仍有 8、13、14、14 条硬冲突。性能改动没有改变这项结果；下一步应按冲突类别提升求解器，而不是仅增加重试次数。
- 后台生成只有一个并发任务，任务进度按尝试次数更新；这是为避免占满本机 CPU 的明确限制。
- 单实例保护以本机数据目录为范围，不提供跨网络或跨机器的协调。
