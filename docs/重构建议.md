# 重构建议

基于 2026-08-30 对 v1.8（08089c6）的全量审查。行号均指该 commit 下的实际文件行。

## 结论

- 代码风格干净：小函数、`monthMeta`/`groupsByPeople` 缓存、纯规则模块 + 加载时断言。问题不在写法，在架构形状。
- 一个 4278 行的 `server/engine.ts`：148 个顶层函数、18 个超 60 行、7 个超 100 行，最长 `repairHardCover` 219 行、`validateRoster` 208 行。
- 96 个函数签名带同一个 `grid: Map<number, Map<string, GridMark>>`，81 处逐字透传同一个 6 参数元组。
- 排班是"贪心修复级联"：`generateRosterGrid`（engine.ts:3805）用 127 行手工排布约 50 次 pass 调用，正确性完全依赖调用顺序。
- 没有回归测试。任何拆分都可能悄悄改变排班结果，先补安全网再动结构。

## P0 先补安全网（重构前置）

- 全仓 `git ls-files` 没有任何 test/spec。唯一测试是 sandwichRest.ts:28、shiftBlocks.ts:22、workStreak.ts:46 里模块加载时执行的裸断言：崩进程、不可筛选、只能靠起服务才跑到。
- 搬到内置 `node:test`（零新依赖），package.json 加 `"test": "tsx --test server/**/*.test.ts"`。
- 加黄金用例：造 3-4 个合成月份（含节假日/请假/想休/加班/canNight=false），把 `generateRoster({seed})` 的 roster + conflicts 存成 JSON 快照，之后每步重构对比。
- 生成必须可确定复现：engine.ts:3773 用 `Date.now()^Math.random()` 兜底，api.ts:65 又重复算一次，两处合并、测试显式传 seed。
- 再加一条不变量：生成后跑 `validateRoster`，把 `countHardConflicts` 与耗时打日志，长期观察是否退化。

## P1 让引擎变纯（顺带消灭参数透传）

- 引擎目前直连 SQLite：engine.ts 内 28 处 `queryAll/queryOne/execSql/persist`（loadPeople:54、loadHolidays:76、loadPrevWeekWork:650 等）。这是无法单测的根因——起引擎就得起 wasm + 磁盘库。
- `MonthPack`（engine.ts:3462）已是现成 DTO。把所有加载搬到 `server/repository/month.ts`，`generateRosterGrid(input, pack)` 变纯函数，黄金测试脱离 DB 运行。
- 引入上下文对象，机械替换签名：

```ts
type Ctx = { grid: Grid; people: Person[]; byGroup: Map<string, Person[]>;
             cells: MonthCell[]; s: Settings; prev: WorkSet;
             prevDay: Map<number, ShiftMark>; rng: Rng };
type Pass = (ctx: Ctx) => void;
```

- 一次删掉 96 处 grid 签名与 81 处 6 参数透传，零行为改动。
- 参数卫生：`canTakeWork`（:911）9 个参数、尾部 3 个是 `intended/ignoreWish/allowOvertime` 位置布尔旗标，改 options 对象。
- 全局可变状态归位：`generateSeed`（:26）→ ctx.rng；`leftoverWeekendExtra`（:221）见"缺陷清单"；`monthMetaCache`/`groupsByPeople`/`mondayMemo` 收进 ctx 生命周期（当前按日期无界增长）。
- `loadPrevWeekWork` 等 DB 边界用 zod 式校验或 `assert ShiftMark`，替掉 :686 的 `as ShiftMark | undefined`。
- 热路径重复扫描：`workCount`（:405）46 处调用、`personTarget`（:243）29 处、`groupMembers` 28 处，每次整月扫描。给 Ctx 加 `dayIndex`（人 × 日 → mark）增量表，或至少 memo 到"上次修改日"。

## P2 规则单一来源（漂移风险最高）

- 覆盖判定三份真相：validateRoster:3308（出硬冲突）、buildStats:3426（出 `gap` 红格）、coverGapCount:3548（给修复用），三处各自展开 `need.work / canSplit / morning / night`。抽 `dayDeficits(cell, members, ctx): Deficit[]`，三处都从它派生。
- 可行性判定两份：`canTakeWork`（:911）会查 wantRest、周上限、次日锁定早班；`forceWorkMark`（:966）不查。合并成一个 `admit(person, date, mark, opts)`，差异用选项表达。
- 派生状态双写：`assignNights`（:1411，185 行）手工维护 `nightCount`，4 处增量更新（:1424/:1481/:1494/:1514）与 `personNightCount()` 并存。统一走一个 NightTally 小对象。比较器里调 `nightClusterPenalty`（内部遍历整月）应预计算。
- 规则表化，与 CONTEXT.md 术语一一对应：

```ts
interface Rule { id: string; severity: "hard"|"soft"; doc: string;
                 check(ctx): Conflict[]; repair?(ctx): boolean }
```

  `validateRoster` 退化为按表循环 + 拼装文案，208 行长函数消失；`repairHardCover`/`repairAttendance`/`repairNightDiff` 共用 `tryFix(ctx, candidates, predicate)` 模板（`snapshotMarks`/`restoreMarks` 已 12/16 处调用，正好包成 `withRollback`）。

## P3 把流水线变成数据

- engine.ts:3805-3931 是 127 行手工顺序：`repairHardCover` 14 处调用、`repairAttendance` 11 处、`repairIsolatedWork` 9 处、`ensureGroupCover` 8 处；`enforceHardConstraints`（:4118）、`repairSoftRound`（:3724）又是另两套顺序。哪一轮先跑决定结果，但没有注释解释为什么。
- 改成 `const HARD_PASSES: Pass[] = [...]` + `runPasses(ctx, passes)`，顺序作为可读、可 diff、可单独禁用的数据。
- 收敛策略散落：23 处手写 `guard`/轮次上限，取值 {8,10,12,16,20,24,40,80} 加外层 {3,6,24}，等于 23 份口头约定的死循环保险。收敛成带日志的 `runUntilStable(ctx, passes, {maxRounds})`，冲突数不降即退出；日志顺便暴露哪些 pass 在互相振荡。

## P4 按域切文件

- 目标结构：`server/engine/{context,grid,seed,coverage,nights,rest,attendance,repair,validate,stats,persist}.ts`，`index.ts` 只做流水线编排。
- 这一步之后 `Grid` 收成一个带 `get/set/works/nights/target/deficits` 的对象，186 处 `markOf(grid, id, date)` 变 `grid.get(id, date)`，`\`\${personId}|\${date}\`` 字符串主键（applyUserMarks:3521、excel.ts:122/:286）收进 Grid 内部。

## P5 服务端与存储

- 生成阻塞：index.ts:247 路由同步执行，最坏 `maxAttempts = 24`（:3776）轮完整流水线卡死事件循环，UI 只有一个"正在生成…"。改任务式（POST 起任务 + 轮询状态），或先降成单轮 + 需要时重排，并把冲突数/耗时回传前端。
- 错误出口：index.ts 只有 1 处 try/catch（:282）。`/api/export`（:457）、`/api/restore`（:497）是 async 且无 catch——Express 4 不接 async rejection，一抛错请求直接挂死。加 `wrap(fn)` 助手 + 4 参错误中间件，永远返回 JSON 错误体（api.ts:22 已按 `{error}` 解析）。
- 校验：`PUT /api/settings`（:43）把 body 直接合进 Settings 存库，`maxWorkPerWeek: "abc"` 或负数会让引擎未定义。写 `normalizeSettings(unknown): Settings`，按 DEFAULT_SETTINGS 逐字段收敛取值域。
- 样板：`year/month` 解析在 index.ts:237/:247/:266/:457 各写一遍 → `parseYm(req)`；`loadPeople` 的行映射在 index.ts:48 与 engine.ts:54 重复 → `personFromRow`；api.ts:52 `date` 拼 URL 缺 `encodeURIComponent`。
- 落盘：db.ts:50 `persist()` = `writeFileSync(db.export())` 整库重写，而 `run()`（:186）每次单格改动都调它。改脏标记 + 200ms 防抖，退出前兜底。
- 原子写：直接覆盖 data.db，掉电即损坏唯一副本。改写 `data.db.tmp` + `renameSync`，保留 `data.db.prev`。
- 事务：`runMany`（:191）只是 `actions(); persist()`，index.ts:120 删人是多语句。用 sql.js 的 `BEGIN/COMMIT/ROLLBACK` 包成真事务。
- 恢复：`restoreFrom`（:222）把上传字节直接写成 data.db，不校验是否合法 SQLite。先 `new SQL.Database(buf)` 打开并查 people 表，成功再换。
- 迁移：`maxNightDiff === 5 → 3`（:122）与 `getSettings` 里每次读都 `delete` 6 个历史字段（:200）是两处硬编码。建 `schema_version` + 有序迁移数组，normalizeSettings 独立成函数。
- 小项：`prepare` 后缺 `try/finally { free() }`（:163/:179），抛错即泄漏语句。
- 可选：服务只绑 127.0.0.1（index.ts:534，很好），但 `app.use(cors())` 默认 `*` 等于允许用户浏览器里任意网页对本地库读写。SPA 与 API 同源，`cors()` 可直接去掉。

## P6 前端

- CalendarPage.tsx 525 行、9 个 useState、表格 + 编辑弹窗 + 导入弹窗 + 请假 + 冲突提示混在一处。按容器/表格/弹窗切块，`importOpen/importFile/importTargetY/importTargetM/importResult` 挪进导入弹窗自有状态。
- `api.setCell/setWish/setFlag` 都返回整月 payload，CalendarPage.tsx:108 按到达顺序 `setData`，连点格子会旧覆盖新。加请求序号守卫，成本极低。
- 跨页刷新靠 App.tsx:14 的 `tick` 计数器 + 每页各自 `load()`。抽 `useRoster(year, month)`（含 seq 守卫、busy/error），`tick` 退休。
- api.ts:72 `importExcel` 手抄一遍 req 的错误处理（multipart 不能带 JSON 头）→ 补 `reqForm()`。
- App.tsx:8 `const now = new Date()` 在模块作用域，跨月挂着的窗口不会自动翻页；App.tsx:51 `RulesPage` 只拿到 `setMonth` 没有 `setYear`，与另两页不对称。

## 缺陷与死代码清单（可立刻清）

- keepLocked 是假功能：index.ts:250 → engine.ts:3809 → `applyFixed` 的 `_keepLocked`（:155 未使用），`persistGenerated(…, keepLocked)`（:4234）也没用它。`generateRosterGrid` 里 `applyFixed`/`applyUserMarks` 都只按 `Assignment.locked` 列决定锁定，与入参无关；`currentRoster` 更直接传字面量 `true`（:3759）。结论：「生成」与「重排未锁定格子」（CalendarPage.tsx:95）走完全相同的代码，只有 loading 文案不同；且 persistGenerated 无条件 `locked = cell.locked || cell.wantRest ? 1 : 0`，把整次结果连同想休永久锁死。要么实现该选项，要么删掉，别留着误导。
- `leftoverWeekendExtra`（:221）只写不读：`setMonthWorkExtra` 有 4 处调用（含 validateRoster:3163、buildStats:3367 两个只读路径），但没有任何地方读取，`leftoverWeekendQuota` 算完就丢。周末值班配额的语义缺口，需要你确认是回归还是废弃。
- `validateRoster`/`buildStats` 在改模块级状态，已经不纯；`generateSeed` 全局同理，生成一旦异步化就会串味。
- 未被调用的函数：isWorkOnDate(:330)、shiftBlockSwitches(:524)、weekLegalWorkInMonth(:817)、isPartialWeek(:841)、nightNeed(:1097)、fillLegalAttendance(:2949)；另有 calendar.ts 的 lastWeekNum/isBridge/legalWorkDayCount、holidays.ts 的 HOLIDAYS_2026。合计约 120 行。
- tsconfig.server.json 缺 `noUnusedLocals`/`noUnusedParameters`（前端 config 有），上面的死参数与死函数因此隐身。补上再 `npx tsc -p tsconfig.server.json`。
- 隐私：db.ts:13 把 14 位真实同事姓名与组别硬编码进源码，仓库远端在 GitHub。建议换占位名（"同事1" + 广州/佛山/中山清远）或改读 `templates/seed.json`；若仓库公开，历史需要用 `git filter-repo` 清理。
- 文档漂移：README.md 让双击 `制作绿色包.bat`，该文件既不在工作区也不在 `git ls-files`（只有 `启动排班.bat`）。
- 数据即代码：holidays.ts 把 2024-2026 国务院假期写死在 TS，每年要改代码 + 重新打包。挪 `data/holidays.json`（`resolveJsonModule` 已开），绿包只需替换数据文件。
