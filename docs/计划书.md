## 2. 当前最大问题（先于继续拆文件）

黄金月份在固定 seed 下 **换 24 次种子仍清不掉硬冲突**，生成因此总是跑满 `maxAttempts = 24`。放宽夹心休硬约束到 2 之后（2026-09-01）：

| 月份 | 耗时 | 硬冲突 | 主要类型 |
| --- | ---: | ---: | --- |
| 2026-02 春节 | 13 s | 5 | 出勤多 1～3 天；中山清远晚班极差 4 |
| 2026-05 劳动节 | 78 s | 10 | 夹心休 3～4 天；出勤超标；满周不足；佛山晚班极差 |
| 2026-08 普通月 | 139 s | 10 | 出勤超标；夹心休 3 天；穿插；短班 |
| 2026-10 国庆 | 82 s | 10 | 出勤超标；夹心休 3 天；穿插；佛山晚班极差 |

硬冲突几乎全是三类，且互相顶牛：

1. **夹心休仍超 2 天**（3～5；第 2 个已不记硬冲突）
2. **出勤对不齐法定工作日**（多排 1～3 天）
3. 偶发：**晚班极差 > 3**、**晚接早**、**短班**、**班次穿插**

界面上点「生成」会卡住事件循环 20～150 秒，最后仍红字。黄金测试只断言 JSON 相等，**没有「硬冲突必须为 0」**，所以 1.9 的安全网锁住的是「结果不变」，不是「结果可用」。

继续按 1.8 计划切 `engine/` 目录，不会让班表更好用。下一阶段以 **质量 + 速度** 为主，结构跟在后面。

### 阶段 1 — 生成质量（本计划的核心）

目标：四个黄金月 **硬冲突尽量到 0**；若规则本身无解，把无解写成产品决策（第 5 节），不要用红字假装「生成失败再重试」。

建议顺序：

1. **加质量断言，而不是只锁快照。** 例如 `assert.equal(hard, 0)` 或 `assert.ok(hard <= N)`。现在改引擎只要 JSON 变就会红，但硬冲突从 14 降到 3 也会红——应允许 `UPDATE_GOLDEN=1` 更新快照，同时把硬冲突数当作独立门槛。
2. **用 `ROSTER_PIPELINE=1` 看哪一轮引入夹心休 / 超出勤。** `runUntilStable` 已打 `hard=`；给 `repairIsolatedWork`、`repairHardCover`、`repairAttendance` 各打一条「本 pass 后夹心休人数、超出勤人数」。
3. **夹心休硬约束已放宽到 2**（[ADR 0001](./adr/0001-coverage-may-force-second-sandwich.md)）。生成仍尽量压到 1；3 天及以上仍红。覆盖修复拆出单休后，要把多于 2 的回收掉，并排在出勤修复之后。
4. **`canTakeWork` 与 `forceWorkMark` 仍两套可行性。** 覆盖不够时走 `forceWorkMark`（不查想休、周上限），这是超出勤和夹心休的主要入口。收成一个 `admit(person, date, mark, opts)`，差异只用选项表达。
5. **覆盖判定三份真相**（`validateRoster` / `buildStats` 的 `gap` / `coverGapCount`）抽 `dayDeficits`，避免修覆盖和亮红格各算各的。

验收：黄金四个月硬冲突数写入本计划的对照表；至少普通月（8 月）和春节月（2 月）硬冲突为 0，或书面记录为何无解。

### 阶段 2 — 生成速度

卡顿的根因不是「24 次里总有一次特别慢」，而是 **硬冲突从未到 0，所以 24 轮全跑**。质量上去之后，成功路径应 1 轮结束。

在硬冲突还没清零之前，也可以先做：

- 冲突数连续 N 轮不降就停，不必跑满 24。
- 生成改任务式（POST 起任务 + 轮询），或至少把冲突数 / 耗时回传前端，不要只写「正在生成…」。
- 热路径：`workCount`、`personTarget` 仍整月扫描。Ctx 上维护人 × 日增量，或至少 memo 到上次改格。

验收：硬冲突为 0 的月份，生成（含日志）< 3 秒；测试套件 < 30 秒。

### 阶段 3 — 规则表化 + 流水线收干净

1.8 的 P2 / P3 尾巴：

- `validateRoster`（约 200 行）改成 `Rule[]` 循环 + 拼文案。
- `HARD_TAIL_PASSES` / `FINISH_PASSES` 仍是手工长列表（`repairHardCover` 反复插入）。收成「冲突类 → 修复 pass」的数据，用已有的 `runUntilStable`（格子指纹不变就停）。
- 散落的 `guard`（取值 8 / 10 / 12 / 16 / 20 / 24 / 40 / 80）收到 `runUntilStable` 的 `maxRounds`。
- `assignNights` 手工维护 `nightCount`，与 `personNightCount()` 双写。收成一个 NightTally。

验收：黄金快照可更新，但硬冲突数不得回升。

### 阶段 4 — 按域切文件

`server/engine.ts` 仍 3859 行。质量稳定后再切：

```
server/engine/{context,grid,seed,coverage,nights,rest,attendance,repair,validate,stats}.ts
```

`index.ts` 只编排 Pass 数组。`Grid` 收成带 `get/set/works/nights/target/deficits` 的对象；`personId|date` 字符串主键收进 Grid。

`validateRoster` / `buildStats` / `applyUserMarks` 在缺缓存时仍回落到 `loadPrevWeekWork` 等 DB 调用。切文件时改成「缺 pack 就抛」，生成路径保持纯函数。

### 阶段 5 — 服务端与前端收尾

**服务端**

- `/api/export`、`/api/restore` 是 async 且无 catch，Express 4 不接 rejection。加 `wrap(fn)` + 4 参错误中间件，永远返回 `{ error }`。
- `PUT /api/settings` 把 body 直接合进 Settings。写 `normalizeSettings(unknown)`，按 `DEFAULT_SETTINGS` 收敛取值域。
- `year/month` 解析抽 `parseYm(req)`。
- 落盘：脏标记 + 200ms 防抖；写 `data.db.tmp` + `renameSync`，保留 `data.db.prev`。
- `runMany` 用 sql.js 的 `BEGIN/COMMIT/ROLLBACK`。
- `restoreFrom` 先 `new SQL.Database(buf)` 打开并查 `people`，成功再换。
- `schema_version` + 有序迁移，去掉 `maxNightDiff === 5 → 3` 和每次读都 `delete` 历史字段。
- 节假日从 `holidays.ts` 挪到 `data/holidays.json`（`resolveJsonModule` 已开）。

**前端**

- CalendarPage 按容器 / 表格 / 弹窗切；导入状态进导入弹窗。
- `api.setCell/setWish/setFlag` 连点会旧响应覆盖新状态 → 请求序号守卫。
- 抽 `useRoster(year, month)`，`App.tsx` 的 `tick` 退休。
- `api.ts` 补 `reqForm()`；`deleteHoliday` 的 date 要 `encodeURIComponent`。
- `App.tsx` 模块作用域的 `new Date()` 跨月不会翻页；`RulesPage` 缺 `setYear`。

## 4. 建议落地顺序

```
阶段 0 机械清理
    → 阶段 1 生成质量（夹心休 / 出勤 / admit / dayDeficits）
        → 阶段 2 生成速度（早停 + 热路径；质量达标后 1 轮结束）
            → 阶段 3 规则表化
                → 阶段 4 切文件
                    → 阶段 5 服务端 / 前端
```

不要在阶段 1 完成前做阶段 4。切文件会让「哪一轮引入夹心休」更难跟。
